## Naming
- Feature name in code, folders and UI text: **Meal import** (`Features/MealImport`, `MealImport*`), matching
  the `meal_imports` table and the rest of the app. Not "Recipe".
- Branches: Linear's `gitBranchName` for each issue.

## Contract

### DB-1: `public.meal_imports`
| Column | Type | Notes |
|---|---|---|
| id | uuid PK | generated by the client before insert |
| created_by | uuid | `auth.uid()` |
| status | text | `pending` \| `succeeded` \| `failed` |
| ... | | |

RLS: owner can SELECT and INSERT (status must be `pending`); owner can UPDATE `pending` → `failed` only.
Realtime: table is in the `supabase_realtime` publication.

### JSON-1: `meal_imports.parsed_meal`
`{ "Name": string, "Recipe": string (steps joined by "\n"), "Ingredients": [{ "Name": string, "Amount": string }] }`.
PascalCase. Duplicated in two projects (`MealImportPayload` in Functions, `ParsedMeal` in Shared), so keep the
names identical.

### HTTP-1: `POST /api/ScrapeRecipe`
- Request body: `{ "jobId": uuid, "url": string }`. Auth: `x-functions-key` header.
- Responses:
  - `400`: bad body.
  - `200`: the row now reflects the outcome.
  - `502`: the row couldn't be reached. The client then marks the row failed.
- The response is an ack only. The row is the source of truth.

### CFG-1: client config `MealImportFunction: { url, key }`
In every `appsettings.*.json` (MauiWASM and MAUI). Development url `http://localhost:7071`. The production key is
injected at deploy time from the secret `MEAL_IMPORT_FUNCTION_KEY`, never committed.

### API-1: `IMealImportStateContainer` (consumed by the UI)
List the members the consumer may use, with one line each on behaviour (e.g. `StartImport(url) → Result`,
`JobStatus`, `CanContinueInBackground`, `ContinueInBackground()`, `OnStateChanged`, threading notes).

## Decisions

## Integration and release

- Integration test: which branches are combined, and the end-to-end path to click through.
- Production checklist items for this feature: new secrets, app settings, CORS origins, migrations, keys.
- Post-deploy check: e.g. "import a recipe on the live site; fast success, background, failure".

## Change log
Date: what changed in the contract, and which sessions were told.
